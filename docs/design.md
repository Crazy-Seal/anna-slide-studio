# 幻灯片工坊 — 技术方案（v1）

> 状态：待评审 · 目标平台 Anna staging（manifest schema 4） · 交付物：一个可发布、他人可安装使用的 Anna App

---

## 1. 一句话定义

**把一句话变成一份能下载、能继续编辑的 .pptx 文件。**

不是"生成一堆幻灯片文案"，是把"开会前 30 分钟做 PPT"这件事压缩到 5 分钟：输入主题 → 确认大纲 → 拿到成品文件。

### 目标（v1 闭环）

| # | 能力 | 验收标准 |
|---|---|---|
| 1 | 输入主题，生成结构化大纲 | 5 秒内返回，页数可指定 5–12 |
| 2 | 大纲可编辑（改标题/删页/调序） | 改动后重新生成正文时生效 |
| 3 | 按大纲生成每页内容 | 版式、要点、讲稿备注齐全 |
| 4 | 16:9 画布实时预览 | 可在页内直接改字 |
| 5 | 导出真正的 .pptx | PowerPoint / WPS 能打开，文字可编辑 |
| 6 | 额度可见 | 显示剩余额度与本次消耗 |

### 非目标（v1 明确不做）

- ❌ AI 配图（图片模型 12–42 CU/张，会瞬间烧穿额度）
- ❌ 联网调研 / 深度模式（v2）
- ❌ 多人协作、云端保存、账号体系（用平台 storage 做本地草稿即可）
- ❌ 导入 .docx / .md 作为输入（v2）
- ❌ 自定义模板上传（v1 只提供内置主题）

## 3. 系统架构

全部逻辑跑在**一个沙箱 iframe** 内。没有后端、没有子进程、没有数据库。

```
iframe (bundle/)
├── ui/          界面渲染、大纲编辑、画布交互
├── ai/          prompt 构造、调用 llm.complete、解析与校验
├── model/       deck 数据结构 + 校验器 + 修复重试
├── render/      版式渲染器（DOM/CSS，确定性排版）
├── export/      PptxGenJS → ArrayBuffer → 上传 → 保存
└── quota/       额度读取与消耗展示

        ↕ postMessage（AnnaAppRuntime SDK）

Host API
├── llm.complete      生成大纲 / 正文（消耗用户 CU）
├── llm.catalog       读 remainingCU
├── files.*           .pptx 存储 + 宿主代下载
└── storage.*         草稿（可选）
```

**关键边界**：iframe 无文件系统、无网络（CSP `connect-src 'self'`）、无法执行命令。一切特权操作必须经 Host API。

## 4. 关键决策

### D1 · 用工作流，不用 Agent

| | 工作流（选定） | Agent |
|---|---|---|
| 控制流 | 代码写死，`await` 两次 | 模型自主决定下一步 |
| 模型调用 | 2 次 | 3–8 次 |
| 额度 | 基准 | 数倍 |
| 可测性 | 高（输入输出确定） | 低 |

**理由**：做 PPT 是纯生成任务——没有"作用于外部世界"的动作可调。平台工具是 `web_search` / `doc_read` / `image_generation`，没有也不可能有"渲染一页幻灯片"这种工具。挂 agent 的结果是多转几圈花几倍 token，产出同样的 JSON。

Agent 只在需要联网调研时有价值 → 留作 v2「深度模式」。

### D2 · 大纲与正文拆成两次调用

**理由**：用户浪费额度的真正原因不是"某页写得差"，而是"整份做完发现结构就不对"。一次大纲调用几分钱，一次整份重生成贵十倍。把结构确认前置，是最高性价比的省额度手段。

**代价**：多一次交互打断。换来的是可控。

### D3 · 不捆绑任何 Executa

manifest 留空 `required_executas` / `optional_executas`。

**理由**：schema ≥ 2 的纯 UI App 允许两个数组都为空（文档明确）。少一层子进程 = 少一类故障（进程崩溃、协议超时、发布时 tool_id 校验失败）。

### D4 · 模型只产出内容，排版交给确定性代码

模型输出结构化 deck JSON；每个 `layout` 在渲染器里对应固定几何布局。文字超长由**代码**做字号自适应，不交给模型"注意不要写太长"。

**理由**：把"排版是否正确"变成可验证的确定性逻辑，而不是模型的自觉性。

### D5 · 不生成图片

图片模型 12–42 CU/张，10 页配图 = 120–420 CU。1000 额度三次就没了，而这道题**明确按额度使用评分**。

视觉表现力改由：几何色块、字号层级、留白节奏、主题配色实现——这些是代码可控的，也永远不会有"AI 味插图"。

### D6 · 导出在浏览器内完成

浏览器内用 PptxGenJS 生成 OOXML 字节流 → Host API 上传 → 宿主代下载。

**理由**：没有后端可放渲染服务；且必须产出**真 .pptx**（文字可编辑），而不是图片拼贴或 PDF。

## 5. 数据契约

### 5.1 Deck JSON

```jsonc
{
  "title": "2026 Q3 业务回顾",        // ≤ 40 字
  "subtitle": "产品团队 · 10 月",      // ≤ 30 字，可空
  "theme": "editorial",               // editorial | minimal | bold | tech
  "slides": [                         // 5–12 页
    {
      "layout": "title",              // 见下表枚举
      "title": "2026 Q3 业务回顾",
      "subtitle": "产品团队 · 10 月",
      "notes": "开场 30 秒，点明本次回顾的三个问题"   // 讲稿备注 ≤ 200 字
    },
    {
      "layout": "metrics",
      "title": "三个关键数字",
      "metrics": [                     // 2–4 项
        { "value": "+38%", "label": "月活增长" },
        { "value": "4.2",  "label": "NPS" }
      ],
      "notes": "..."
    },
    {
      "layout": "bullets",
      "title": "本季度的三件事",
      "bullets": ["完成核心链路重构", "上线企业版", "搭建数据看板"],  // 2–5 条，每条 ≤ 28 字
      "notes": "..."
    },
    {
      "layout": "two_col",
      "title": "做得好的 / 待改进的",
      "columns": [                     // 恰好 2 列
        { "heading": "做得好的", "items": ["交付节奏稳定", "线上事故下降"] },
        { "heading": "待改进的", "items": ["需求变更频繁", "跨团队依赖多"] }
      ],
      "notes": "..."
    },
    {
      "layout": "quote",
      "title": "用户怎么说",
      "quote": { "text": "终于不用周五晚上赶 PPT 了", "attribution": "某客户 · 产品经理" },
      "notes": "..."
    },
    { "layout": "closing", "title": "谢谢", "subtitle": "Q&A", "notes": "..." }
  ]
}
```

### 5.2 版式枚举（固定 7 种）

| layout | 用途 | 必填字段 | 约束 |
|---|---|---|---|
| `title` | 封面 | `title` | 仅首页 |
| `agenda` | 目录 | `bullets` | 3–6 条 |
| `bullets` | 要点 | `bullets` | 2–5 条，每条 ≤ 28 字 |
| `two_col` | 对比 | `columns` | 恰好 2 列，每列 2–4 条 |
| `metrics` | 数字 | `metrics` | 2–4 项，`value` ≤ 8 字 |
| `quote` | 引用 | `quote` | `text` ≤ 60 字 |
| `closing` | 结尾 | `title` | 仅末页 |

### 5.3 校验规则（代码强制，不靠模型自觉）

1. `slides.length` ∈ [5, 12]
2. `layout` ∈ 枚举
3. 首尾页 layout 正确
4. 各 layout 必填字段存在且类型正确
5. 字数超限 → **不报错，截断**（比整份失败体验好）
6. 非法 layout → 降级为 `bullets`
7. 缺 `notes` → 补空字符串，不阻断

## 6. Prompt 设计

三份 prompt，都是产品资产：

| 常量 | 用途 | 关键约束 |
|---|---|---|
| `OUTLINE_SYSTEM` | 生成大纲 | 只输出 JSON；给出每页主题 + 叙事线；禁止空洞标题 |
| `DECK_SYSTEM` | 生成正文 | 只输出 JSON；版式枚举；字数上限；中文标点；禁止编造数据 |
| `REPAIR_SYSTEM` | 修复坏 JSON | 只修补，不重写；原样保留合法部分 |

共用规则（写在两份 system 里）：

- 「只输出 JSON，不要 markdown 代码块，不要解释文字」
- 给出**完整示例**（few-shot 比"请严格遵守格式"有效得多）
- 「不要编造具体数字；没有数据就用定性表述」
- 「中文内容使用中文标点；英文专有名词保留原文」

> ⚠️ SDK **没有** `responseFormat` / `jsonSchema`（已核实源码，无此字段）。所以强制结构化输出不存在，只能靠 prompt + 校验 + 重试。

## 7. 容错

```
拿到模型输出
  ├─ 剥离 ```json 围栏 / 前后噪声
  ├─ JSON.parse 成功?
  │    ├─ 是 → schema 校验
  │    │        ├─ 通过 → 渲染
  │    │        └─ 失败 → 修正可修项（截断/降级/补默认）
  │    └─ 否 → REPAIR_SYSTEM 重试 1 次
  └─ 仍失败 → 展示错误 + 「重试」按钮（不自动重试，避免烧额度）
```

**重试上限硬编码为 1 次**。任何情况下不自动重试第二次——额度是别人的钱。

其他容错：

- `stopReason === "maxTokens"` → 判定截断，提示"内容过长，已精简"
- `quota_exceeded` → 明确提示额度不足，给引导文案
- `llm_disabled`（本地 `--no-llm`）→ 显示占位数据，不崩

## 8. 导出链路

```
PptxGenJS 生成 ArrayBuffer
   ↓
files.upload_init({ path, content_type, size })   → presigned PUT URL
   ↓
fetch(PUT)
   ↓
files.upload_finalize({ path })
   ↓
files.download({ path, filename })                → 宿主弹出保存对话框
```

### ⚠️ 待验证假设（M3 第一件事）

`files.upload_init` 返回的是**跨域 R2 预签名 PUT**，而 bundle 的 CSP 是 `connect-src 'self'`。若平台未自动放行 R2 域名，第 3 步会被 CSP 拦掉。

**这不是靠读文档能确认的**，必须真实环境实测。已准备降级方案：

| 路径 | 做法 | 风险 |
|---|---|---|
| 主路径 | `files.*` 两段式上传 + `files.download` | 可能被 CSP 拦 |
| 降级 A | `upload.inline`（单次 RPC，无跨域 PUT）+ `<a download>` | 依赖 sandbox `allow-downloads` |
| 降级 B | 直接在页面内提供 `download_url` 链接，让用户在浏览器打开 | 体验差但一定能用 |

M3 第一步就是写一个 20 行的冒烟页，把三条路径都试一遍，用事实定方案。

## 9. 额度预算

平台**未公开文本生成的 CU 单价**（只公开了图片/TTS/视频/搜索）。所以策略是：**不估算，先测量**。

- 首次真实调用后读 `_meta.quotaConsumed`，反推单份 deck 成本
- 实测结果：一份 8 页 deck = **0.70 CU**（详见 [实现笔记](implementation-notes.md)）

已知可算的部分：

| 项目 | CU |
|---|---|
| 图片生成 | 12–42 / 张 ← 不做 |
| web search | 0.5–13.8 / 次 ← v1 不做 |
| 文本生成 | 按 provider 成本 × 系数，未公开单价 |

**额度护栏**（产品化，直接对应评分项）：

1. 工具栏常驻显示 `剩余额度`
2. 生成前显示预估（基于实测均值）
3. 生成后显示本次实际消耗
4. 单次生成硬上限 2 次模型调用
5. 不做任何后台预生成 / 静默调用

```

├── fixtures\
│   └── replies.jsonl       mock LLM 应答（M0 用）
└── bundle\
    ├── index.html          骨架 + 样式变量
    ├── app.js              入口，编排工作流
    ├── js\
    │   ├── ai.js           prompt 常量 + 调用 + 解析
    │   ├── deck.js         schema + 校验 + 修复
    │   ├── render.js       7 种版式的 DOM 渲染 + 字号自适应

**不引入构建工具**：没有 webpack/vite。原生 ES Module + `<script type="module">`。理由——产物本来就是静态文件，多一层构建只会多一处失败点，且 CSP 对 inline/eval 有限制，越简单越安全。

## 13. 风险登记

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | `files.upload_init` 的 PUT 被 CSP 拦 | 导出不可用 | 三条路径实测 + 降级方案（§8） |
| R2 | 文本生成 CU 单价未知 | 难以预估消耗 | 先测量再展示，不猜 |
| R3 | 中文 JSON 更易解析失败 | 生成失败率上升 | 降 maxTokens 提密度；修复重试；宽松解析 |
| R4 | 沙箱 `allow-downloads` 生产环境行为未知 | 保存对话框不弹 | 用宿主代下载 `files.download` 规避 |
| R5 | PptxGenJS 体积（~500 KB） | 加载慢 | 本地内置 + 懒加载（点导出才载入） |
| R6 | 审核因 listing 文案/截图不合格被驳回 | 上线延期 | 提前按 listing 规范准备素材 |
